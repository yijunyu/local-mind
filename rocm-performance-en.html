ROCm, Vulkan and PolyStrata on gfx1151

One box — Ryzen AI Max+ 395, Radeon 8060S, 128 GB unified memory — and the question the AMD column keeps raising: would another inference engine serve these models better? For dense models the answer is arithmetic rather than opinion. Every figure below is measured on the machine.

Answer — governing thought

Dense decode here is a bandwidth line, not an engine result: every ROCm dense row from 8B to 32B lands within 4% of 193 GB/s. The backend is worth about 7%; n-gram drafting is worth 3.7×.

Bandwidth Six dense models, 8B to 33B, all reading at the same rate — because that rate is the memory system. ›
B1
A dense model must read every weight for every token, so its decode rate is bandwidth divided by file size and nothing else. Multiplying this page's dense rows out: Qwen3-8B 193, Qwen3-14B 199, Muse Glimmer 30B 193, Qwen3.8-27B 191, Qwen3-32B 192 GB/s. Five models, five sizes, one number.
B2
That number is the hardware: about 215 GB/s sustained on this box, against the M1 Ultra's 800. It is why the Macs lead this page on dense decode, and it is not reachable by kernel work on either side.
B3
So a dense model's rate is predictable before you download it: ~208 GB/s ÷ the bytes it reads per token. Nanbeige4.3-33B reads 20.11 GB of its 20.78 GB file per token — the remainder is the embedding table, read a row at a time — and measured 10.33 tok/s, which is 207.7 GB/s. The ceiling itself.
B4
Tested by prediction rather than asserted. Before downloading the IQ4_XS quant of the same model, its tensor table gave 18.00 GB per token, so dividing predicted 11.56 tok/s. Measured: 11.52 ± 0.01 — out by 0.35%. Both quants land on the same read rate, 207.7 and 207.4 GB/s, so the entire 11.5% gain is the smaller read and nothing else. Prefill was unchanged (307.4 against 306.8 tok/s), exactly as it should be when only the bytes move and not the arithmetic.
B5
Which makes quantization a division, not an experiment: at this read rate Q3_K_M projects to ~13.5 tok/s and IQ2_M to ~18. The cost is quality, and it is not free — IQ4_XS measured +1.55% perplexity against Q4_K_M on identical flags, about a seventh of the speed it bought, and not significant on that corpus. It was not adopted here: n-gram drafting already gives this model 3.7× on the work it does, which makes 11.5% on the undrafted baseline a poor reason to spend quality on a coding model.
Backend Real but small on dense decode (+7%); large on MoE (+18%), and it reverses on prefill. ›
K1
The controlled dense pair — Qwen3.8-27B, same llama-bench instrument, 16.2 GiB on ROCm against 16.3 GiB on Vulkan: 11.0 vs. 11.74 tok/s, +6.7% for Vulkan. That puts Vulkan at 96% of the sustained ceiling and ROCm at about 89%.
K2
On MoE the gap is wider and the phases disagree. MiniCPM-V 4.7 35B-A3B, 256-token decode on the same Q4_K_M file with identical flags: ROCm llama.cpp 58.0–58.4 against Vulkan 68.2–68.9 (median 68.6), +18%. Vulkan gives back −10% of prefill for it (1,127 vs. ROCm's tuned 1,255), which is accepted here because interactive serving is decode-dominated.
K3
PolyStrata is retired — 61.4 tok/s decode and ~1,055 prefill, against Vulkan's 68.6 and 1,127, so it lost on both phases and production moved on 2026-10-17. Note those two PolyStrata figures were taken on the smaller mixed-Q3 file rather than the Q4_K_M above, so they flatter it slightly. Its kernels were also model-shaped, so a Llama-architecture model was never covered by it.
K4
An independent measurement points the same way: DeepSeek V4 Flash on this hardware, Vulkan 231.8 prefill / 18.9 decode against ROCm's 207.9 / 14.8.
K5
MoE is where this box looks good at all — 56–69 tok/s — because only a fraction of the weights are read per token. The bandwidth line above is a dense-model constraint, not a property of the machine.
Drafting 3.7× on an edit-this-file prompt — larger than any backend change, and narrower. ›
S1
Since dense decode is bandwidth-bound, the only large win is to stop reading the weights once per token. n-gram lookup needs no draft model — the candidates come from the prompt. On Nanbeige4.3-33B: 10.1 → 37.9 tok/s, with 249 of 249 drafted tokens accepted on “here is a function, rename two identifiers, print it back”.
S2
It is workload-shaped, not universal. On free-form prose the same flag gives 10.85 against 10.14: nothing gained when the lookup misses, and nothing lost either. It suits agentic and coding work, where most output tokens already appear in the input, and is irrelevant to chat.
S3
⚠ It costs bit-exact reproducibility. Greedy output was byte-identical to non-speculative decode on the copy-heavy prompt and diverged on prose — the same claim in different words. Two draft lengths produced the same divergent text, which points at the numerics of verifying a batch rather than a drafting fault.
vLLM / SGLang Not wrong, but answering a different question: they win on batched concurrency, which this box does not have. ›
V1
Their advantage grows with concurrency, and local serving here is one stream at a time. At C=1 on a large model llama.cpp led in a published Strix Halo comparison (13.57 vs. 10.34 tok/s); vLLM led on small dense models and at every C ≥ 2.
V2
SGLang has no stock gfx1151 lane. Running it required patched AOT targets, import guards, an allow-list entry and a hand-named quantization method — and it still trailed vLLM at every matched point.
V3
There is a cost no benchmark shows: the model arbiter on this box persists each slot's KV across a model swap through llama.cpp's /slots/{id}?action=save|restore. That is what turns 13,967 ms of prefill back into 106 ms after a full stop and start. Neither vLLM nor SGLang offers it, so adopting one would trade a measured 130× prefill recovery for, at best, single-stream parity.

Caveats that travel with the number

The dense Vulkan rows were taken on a newer llama.cpp than the dense ROCm rows — build 2881e5b8 against 3173a56. So part of that +6.7% may be builds rather than the API, and that pair is suggestive rather than clean. The ROCm-versus-Vulkan MoE pair in K2 is clean: same file, same flags, same day. The PolyStrata figures in K3 are not part of it — different engine, different quantization, no shared flags.

Decode figures are llama.cpp llama-bench, tg128, r=3 — the same instrument and token count as the M1 Ultra rows, so those columns compare to each other. The MoE backend table is a 256-token server measurement. The 3.7× drafting figure is a server measurement over 320 generated tokens, because llama-bench does not drive speculative decoding. Sizes are as llama-bench reports them, in GiB.

Nanbeige4.3-33B's own quality claims are the vendor's and unreplicated. Its figures here are throughput, which is all this page measures. It is served at 131,072 context with a q8_0 KV cache rather than the 524,288 it advertises: its cache costs 208 KiB/token at f16, ten times MiniCPM's, so the full context would want 104 GB of cache on a 128 GB box.

Quantizing that cache costs nothing perplexity can see, including at the context actually served. Against an f16 cache on wikitext-2, paired per chunk: +0.06% at 2,048 context, −0.17% at 16,384 and −0.16% at 65,536 — a full slot — none of them significant. All three were run because cache quantization error ought to accumulate with context, and a short-context result alone would have proved little; across a 32× range it does not grow, and the two long points agree closely while sitting nominally below zero, which is what noise looks like. Bounds are ±0.35%, ±0.18% and ±0.76%: the full-slot run is the loosest of the three, because this corpus affords it only four chunks, so the no-accumulation case rests on the agreement between the 16k and 64k estimates rather than on the 64k bound alone. Comparing the absolute figures across rows would be a mistake — the longer runs need larger corpora, so only the paired deltas within each row are comparable.
